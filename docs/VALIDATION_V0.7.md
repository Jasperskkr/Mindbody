## 交付功能与保持兼容的部分

- 3 个 SourceDocument，4 张原知识卡稳定 ID/原正文保留。来源/内容分离，sourceId/sourceVersion 关联；授权、来源核对、专业审核、证据类型分别表示，传统理论不当作现代疗效证据。
- KnowledgeChunk 的 TS/Python 结构已定义；没有生成片段/Embedding/向量索引。
- CLI 支持校验、重复 ID/来源检查、来源登记、草稿、版本修改、核对/专业审核记录、归档、正式快照构建及只读一致性检查。
- 内容修改自动升版本、回草稿并清除专业审核；来源改版后卡片需要重新核对绑定。归档保留稳定 ID，禁止物理移除或重复使用。
- 正式快照只发布符合生命周期/审核/来源版本/授权条件的卡；源文件保留草稿和归档信息，正式快照全量重建，不累积旧索引。
- 一份白名单评分表达式生成 TS/Python 实现；心理/中医每域独立 Top-K，默认各 2，可配置 1–10；无匹配为空，稳定 ID 排序，不全局截断。
- manifest 检查版本/哈希；knowledgeHash 包含正式内容、来源、规则及生成实现指纹。准备调用前 GET 比较，POST/响应再次比较，旧进程知识变更拒绝服务，要求构建并重启。
- 四个页面和路由保留，来源展示增加卡版本、专业审核/授权说明；原记录存储 v1、每日/历史/趋势/导出/删除、逐次授权和本地预览不变。API 保留原路径/字段，新增可选 hash；旧请求不带仍能用，新版客户端准备调用要求版本一致。

## 手动验收与学习顺序

1. 阅读 KNOWLEDGE_BASE.md，打开 sources.json 和任一作者卡，沿 sourceId/sourceVersion 找到来源，区分核对、专业审核、授权和证据类型。
2. 运行 `pnpm knowledge validate`、`pnpm knowledge:check`，应看到 4 张正式卡和明确的未知全文授权提示。
3. 复制 knowledge 到临时练习目录，按 KNOWLEDGE_MAINTENANCE.md 的 --root 方式新增虚构草稿；build 后正式卡数量不增加。
4. 用 revise 写入虚构短文、标签、关键词和局限，观察 version 递增及 draft 状态；仅测试目录里记录虚构核对后 build，测试检索；归档再 build，应无旧正文残留。现实内容的 source_checked 必须有实际核对，不可照抄测试结论。
5. 正式知识内容改变后 build，重启 API、刷新网页；哈希不一致或服务未重启应停止调用，不能靠手改 generated.json 绕过。
6. 用隔离端口的虚构健康记录回归首页→洞察→预览→取消→再授权 Mock，检查 ID、来源与未填/0；不要把真实记录用作自动化测试。
7. 执行 `pnpm check`。CLI 工具自身不会提交或推送；开发搭档按用户持续授权，在每批检查通过并审查提交范围后提交、推送。生产部署仍需另行授权。

建议的本周学习小任务是先在临时目录完成“一篇虚构来源→一张草稿→发布→归档”的闭环；学会维护流程后，再核实真实文献并撰写原创卡。

## 已知限制与后续接口

- 仍只有 4 张来源核对示例，没有新增临床审核内容；专业审核命令记录人工结果，不核验现实身份/资质。未知复制授权不等于允许复制全文，原网页也未在本轮重新逐页核对。
- 检索为区分大小写的字面关键词/标签，不做语义理解或研究质量自动评价；现代研究证据只是预留类型。量表/数值仍由程序计算，模型仍只能选受控候选 ID。
- Chunk 只定义结构，没有切分器、Embedding、向量库或 RAG 自由生成回答。后续应先处理授权材料/定位/版本撤回，再做检索评测；不能默认上传私人问题或记录。
- manifest 记录当前发布版本/哈希，不是完整不可变历史库；多文件发布无事务，失败时门禁拒用后重建。没有多人并发编辑/审核系统。
- 每次 API 配置/洞察请求会校验小规模知识文件；大规模知识库需测量性能再引入受控缓存/原子快照切换。本地开发不承诺公开服务性能。
- 离线静态网页无法即时得知撤回；必须刷新/重新发布网页并重启 API。旧 V0.6 客户端无新哈希门禁，需升级；新版官方客户端才在 GET 后阻止不匹配 POST。
- 不新增网络/数据库/向量依赖；原本机服务无认证/限流、真实 LLM 实连、小程序/App 等未验证边界继续保留。

## 三个值得学习的知识点

1. **规范化与关联**：来源只保存一份，卡片用 ID/版本关联，生成展示数据；改来源不必手工改很多重复元数据，也不会无声继承旧审核。
2. **作者数据与发布数据分离**：写下内容不代表允许检索。草稿/审核/授权/归档门禁决定是否进入完整生成快照。
3. **版本、哈希与契约测试**：版本表达维护动作，哈希发现内容差异，跨语言测试确认实际行为；三者互补，不能只相信两个文件“看起来一样”。
